command round-trip. `_send_key_event` is deleted with the loop; `tests/test_behavioral_engine.py`
has no test that calls it directly (verified by grep), so nothing else breaks.

## 2. Shift and Backspace — decided explicitly

**Owner after the swap: `BehavioralTyping`.**

**Shift — `BehavioralTyping` owns it, via `_key_identifier`.** The old loop computed
`shift = char.isupper() or char in '!@#$%^&*()_+{}|:"<>?'` and passed `modifiers: 2` on **both**
the keyDown and the keyUp (`behavioral_engine.py:211,214,234`). The new module does not send
`modifiers` at all — measured: every event from `_dispatch_char_sequence` has
`params["modifiers"] is None`. Instead it sends the **shifted face value as `text`**
(`behavioral_typing.py:302-311`): `"H"` → `key="H", text="H"`; `"!"` → `key="!", text="!"`.
This is the correct CDP convention (Chrome derives the modifier from the `text` payload) and is
already covered by `tests/test_behavioral_typing.py`.

**Behaviour that must survive the swap — every one of these:**
1. Uppercase ASCII letters arrive as uppercase `text`, so React/controlled inputs that read
   `event.key`/`event.data` still see `H`, not `h`.
2. Shifted punctuation `!@#$%^&*()_+{}|:"<>?` arrives with its shifted face value.
3. `\n` → Enter, `\r` → Enter, `\t` → Tab, `" "` → Space, `\b` → Backspace, `\x1b` → Escape,
   `\x7f` → Delete (`_NAMED_KEYS`, `behavioral_typing.py:30-38`).
4. `keyUp` carries **no** `text` field (`_dispatch_key_event:331-333`) — matches CDP, and
   matches the old loop, which only set `text` on `keyDown`.

**What the old shift branch must NOT do any more:** stop synthesising `modifiers: 2`. A
character that is *both* carried by `modifiers` and by `text` is the classic double-shift bug.

**Backspace — the branch is deleted, and its intent changes.** The old `if char == "\b"` branch
existed only to serve typo-correction events **that `keystroke_timing` itself manufactured**; the
caller never passes `"\b"`. With `keystroke_timing` no longer in the typing path, no `"\b"` is
ever generated, so the branch is unreachable-by-construction and is deleted rather than ported.
`"\b"` from *user-supplied* text still works, via `_NAMED_KEYS["\b"] → Backspace` (vk 8) — that
is strictly better than before, because the old branch sent `key="Backspace"` with
`code=""` and no virtual key code. Note the consequence: **the live path loses simulated typos**
(§3, observable change 3). `tests/test_behavioral_sim.py` still covers `keystroke_timing` and
must stay green — it tests `behavioral_sim.py` directly, which is unchanged and still used by
the mouse path.

## 3. The speed question — `speed_factor` is **TRANSLATED**

**Decision: `speed_factor` is translated into the `TypingConfig` CPM range at construction.
It is not ignored, and it is not applied as a post-hoc multiplier to the new log-normal delays.**

Two mechanisms existed and they are mutually exclusive — applying both would double-scale:

- old: `dwell` and `flight` are each multiplied by `self._profile.speed_factor`
  (`behavioral_engine.py:204-205`);
- new: `_generate_delays` derives its distribution purely from `cpm_min`/`cpm_max`
  (`behavioral_typing.py:222-225`). There is no multiplier hook on the new path.

**The translation**, applied once in `BehavioralEngine.__init__` when the `BehavioralTyping`
instance is built:

```
cpm_min = round(profile.wpm_range[0] * 5 * profile.speed_factor)
cpm_max = round(profile.wpm_range[1] * 5 * profile.speed_factor)
```

The `* 5` is not arbitrary — it is the old code's own conversion, `cps = base_wpm * 5 / 60.0`
(`behavioral_sim.py:291`). It converts the old words-per-minute unit into the new
characters-per-minute unit so the two are comparable at all. `wpm_range` keeps its meaning
(per-session speed) and `speed_factor` keeps its meaning (the user's fast/slow dial); each
survives, and the user dial still moves typing speed, it just acts on the CPM bounds now.

`TypingConfig._validate` requires `cpm_min >= 1` and `cpm_min <= cpm_max`. The default
`HumanProfile()` has `wpm_range=(45,80)`, `speed_factor=1.0` → `(225, 400)`, valid. The
`from_session` range is `wpm_min ∈ [40,60]`, `wpm_max ∈ [wpm_min+10, wpm_min+40]`,
`speed_factor ∈ [0.7,1.3]` → minimum possible `(40*5*0.7, 50*5*0.7) = (140, 175)`, always valid.
`HumanProfile` is a plain dataclass with no validation, so a caller can still construct an
out-of-range profile; the engine must therefore clamp to `>= 1` and preserve
`min <= max` rather than letting `TypingConfig()` raise during `__init__`.

**Observable consequences — a user who set a speed factor:**

1. *Speed is preserved within the old range.* Measured old-path effective rate at
   `speed_factor=1.0`: 45 WPM → 126 CPM, 60 WPM → 168 CPM, 80 WPM → 220 CPM. New path at
   default config (200-400 CPM) → measured 274-319 CPM effective. So **typing gets ~1.5-2x
   faster at default profile settings**, which is the intended effect of routing through the
   new module, but it is a real change and must be called out in the CHANGELOG.
2. *A user who set `speed_factor` still gets it.* 0.7 still types slower than 1.0, at a new
   absolute baseline. The direction and relative ordering of profiles are preserved; the absolute
   numbers are not.
3. *Simulated typos disappear from the live path* (`behavioral_sim.py:309`). That is deliberate
   (§2) — the new module has no typo concept, and re-adding one was not in scope.
4. **A session's typing speed becomes affected by `TypingConfig`, which is a global, mutable,
   API-mutable setting** (`main.py:2808-2848`, `POST /typing/config`) while `wpm_range` is
   per-session. The engine must take the config by injection (§5) so that `POST /typing/config`
   does not silently retune every live session without a re-attach. **This is the one part of
   the speed decision that needs a human call** — see §3 open question.

## 4. Preserving the disabled case

Two independent flags exist and must both keep working:

1. **`profile.enabled = False`** — handled at `behavioral_engine.py:178-179` *before* anything
   else and **not touched by this change**: the engine delegates straight to
   `self._client.type_text(selector, text)`, which uses the plain `el.focus(); el.value = ...`
   path. Unchanged, and `tests/test_behavioral_engine.py::test_disabled_profile_no_cdp` covers
   the mouse analogue of this.
2. **`TypingConfig(enabled=False)`** — `BehavioralTyping.type_text` (`behavioral_typing.py:155-158`)
   computes `effective_mode = MODE_RAW` and dispatches **no delay** between characters.

**What the engine must do when typing is disabled:** nothing special. It must still call
`type_text`; `BehavioralTyping` resolves the mode itself. The engine must **not** pre-check
`config.enabled` and skip delegation — that would resurrect a second code path.

**Confirming the live path still works with typing disabled:** measured on `47a5a5c`, raw mode
still emits the full key sequence — 3 events per character, keyDown → keyPress → keyUp
(15 events for `"Hi! A"`). So "disabled" means *no human-like delay*, **not** *no typing*: text
still reaches the field. AC-5 below locks this in.

One caveat to record, not to fix here: in raw mode the dispatch still carries the same shifted
`text` payloads, so a disabled profile still types correctly — good — but `MODE_RAW` is chosen
inside `BehavioralTyping`, and the engine's `type_text` return value stays
`{"status": "ok", "operation": "behavioral_type", ...}` in both modes, so a caller cannot tell
from the return dict whether human delays were applied. Not a regression; noted.

## 9. Rollback

One commit, no revert-then-reapply:

```bash
git revert --no-edit <sha-of-the-swap-commit>
```

If the swap is **not yet committed**, the rollback is `git restore --source=47a5a5c --
src/behavioral_engine.py` — but `47a5a5c` must then be named explicitly as the base, and any
uncommitted work by another agent in that file must be checked first (never a bare `git restore`).

The swap must land as **exactly one commit touching exactly two files**
(`src/behavioral_engine.py`, `tests/test_behavioral_engine.py`) so that this revert is total.
Do not split the refactor and the test change across two commits — that would make the revert
leave a test file asserting a behaviour the code no longer has.
